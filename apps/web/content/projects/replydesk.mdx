## Problem

Support teams want AI to speed up replies, but a wrong or invented answer sent to a customer is worse than a slow one. The system needs AI to do the routine work while a person stays in control of what actually goes out.

## What I built

An AI support inbox with human approval, built for a fictional online electronics store whose three support staff answer about 150 emails a day.

- **Four single-purpose agents** handle each customer message: one sorts it by category and urgency, one extracts its details, one drafts a reply, and one checks the draft.
- **A human support agent** then approves, edits or rejects the draft. Nothing is sent without a human decision.
- **Stack:** Next.js and TypeScript, FastAPI with SQLAlchemy and Pydantic, PostgreSQL with Alembic, running in Docker. Each agent is a prompt file run through one OpenAI-compatible client, currently on gpt-oss-120b via Groq.
- **Tests:** 84 API tests on a real Postgres and 2 Playwright tests on the whole Docker stack. A fake model client keeps the tests offline and free.
- **Live demo:** front end on Vercel, API on Render, database on Neon, all on free plans. Choose **Log in → Try the demo** (no password), or write in as a customer at **New message**. The free server sleeps when idle, so the first load can take a minute, and the demo is capped at 25 new messages a day to stay inside the free model quota.

## Key decisions and trade-offs

- **Orchestration in plain Python, not inside the agent tool.** Step order, storage and business rules are ordinary Python code. Each step is saved before the next one starts, so a failure keeps earlier work and a rerun continues from the failed step. Every model call is logged with its input, output, time and error.
- **Code has the last word on facts.** An order ID the model "found" that isn't actually in the message is dropped by code.
- **The model provider is configuration, not code.** The rest of the code only knows `call_agent(agent_name, message)`. The provider changed during the build and the pipeline and its tests didn't have to.
- **Small agents with one job each.** Four focused agents are easier to test and debug than one agent that does everything, at the cost of more calls per message.
- **Validate every agent output.** Each output is checked against a Pydantic schema. If it fails, the step is retried once; if it fails again, the message goes to a manual-handling queue instead of moving on with bad data.
- **A human approves every reply.** This is slower than sending automatically, but it means an AI mistake never reaches a customer without a person seeing it.

## Results

A set of **60 hand-labelled messages** (`eval/emails.csv`, including angry, Hinglish, two-problem, missing-detail and prompt-injection messages) defines the expected category, urgency and details for each message. An eval script scores every run, so a prompt change is measured, not guessed. The second run changed only the sorter prompt (urgency rules checked in order, clearer complaint / billing / refund rules).

## Limits and what I'd do next

- **The AI only knows what's in the message.** It can't look up an order, so drafts often say "the team will check". A read-only order-lookup tool is the obvious next feature.
- **The eval is small:** 60 messages I labelled myself. Good for comparing versions, not for precise claims. Urgency is the weakest measure; most remaining misses are "high" vs "medium" judgement calls.
- **No real email in or out.** Approving marks a reply as sent; messages arrive by form, API or CSV.
- **Background tasks don't survive a restart:** a ticket caught mid-pipeline stays "processing" until it is rerun. A job queue would fix this at higher volume.
- **The login token is in `localStorage`.** An httpOnly cookie with CSRF protection would be safer.
