## Problem

A booking site has one rule it can never break: a seat is sold once. That gets hard when many people try to book the same seat at the same moment. Booking requests also have to stay fast, so slow work like sending emails can't happen while the user waits.

## What I built

A full-stack event booking platform. Users browse events, hold a seat, and confirm a booking. Authentication uses JWTs with two roles, user and admin.

- **Frontend:** Next.js and TypeScript.
- **API:** FastAPI, with PostgreSQL as the source of truth.
- **Booking rules:** picking seats creates an order that holds them for 10 minutes unless it is confirmed. A multi-seat order is all or nothing.
- **Booking history:** every status change (held, confirmed, cancelled, expired) is appended to an `order_history` table, recording whether a person or the system made it. Rows are never edited, and each booking keeps the price it was sold at.
- **Background work:** Celery workers with Redis send confirmation emails, and Celery beat checks for expired holds every 30 seconds.
- **Running it:** the whole stack starts with one Docker Compose command, and the tests run in GitHub Actions on every push.
- **Live demo:** deployed on Render's free plan through a Blueprint (`render.yaml`), redeploying on every push. Log in as `demo@slotwise.dev` / `demo12345`. The free instance sleeps when idle, so the first visit can take about a minute.

## Key decisions and trade-offs

- **Let the database enforce the rule.** The bookings table has a partial unique index: at most one `held` or `confirmed` booking per seat. When two requests try to hold the same seat at once, both inserts reach Postgres; the second waits for the first to commit, then fails with a unique violation, and the API returns `409 Conflict`. There is no "check, then insert" in application code, which is exactly the pattern that breaks under concurrency.
- **All-or-nothing orders without deadlocks.** Every seat in an order is inserted in one transaction, so if one seat is taken the whole order rolls back. Seats are always inserted in id order, so two overlapping orders wait for each other instead of deadlocking.
- **Timed holds before confirmation.** A hold gives the user 10 minutes to confirm without someone else taking the seat. Because holds expire, an abandoned hold doesn't block the seat forever.
- **Slow work in background jobs.** Confirmation emails and hold expiry run on Celery workers with Redis, so the booking request returns immediately. The cost is two more moving parts (Redis and a worker process) to run and monitor.
- **One container on the free host.** Render's free plan allows one web service and no workers, so the deployed image runs FastAPI, Next.js and a Caddy reverse proxy together, and tasks run inline. Seats still free up on time because hold expiry is checked against the clock, not only by the background job.

## Results

- `test_concurrency.py` releases **12 threads at the same instant against one seat** and asserts that **exactly one wins** and the rest get `409`. With the unique index dropped, the same test fails.
- Further tests cover overlapping multi-seat orders (no seat shared, no deadlock) and simultaneous HTTP requests (one `201`, the rest `409`).
- `scripts/race_demo.py` runs the same race against the running API, with **50 users** by default.
- Tests run in **GitHub Actions on every push**.
