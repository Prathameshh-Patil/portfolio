## Problem

For a text classification task there are three very different options: a classical model, a fine-tuned transformer, or an LLM prompted with a few examples. They differ a lot in accuracy, speed and cost, and the right choice depends on all three, not just accuracy. The question: when is a simple model enough, when is fine-tuning worth it, and when should you just call an LLM?

## What I built

A side-by-side comparison on **CLINC150** (`plus` configuration): short user queries labelled with **150 intents plus out-of-scope**.

- **TF-IDF + logistic regression** (scikit-learn).
- **Fine-tuned DistilBERT** (PyTorch, Hugging Face Transformers), with an out-of-scope **confidence threshold of 0.69** chosen on validation.
- **An LLM** (Gemini 3.5 Flash-Lite), zero-shot and few-shot, behind one function so the provider can be swapped.
- **Serving:** the chosen model runs behind a **FastAPI** endpoint in a small CPU-only Docker image, and an **int8 ONNX** copy runs **in the browser** with transformers.js on GitHub Pages (it agrees with the full model on 99.7% of validation queries).
- Tests, lint and formatting run in GitHub Actions on every push.

## Key decisions and trade-offs

- **The same data for every approach.** Comparing all models on the same splits is what makes the numbers comparable.
- **Choose on validation, report on test, once.** Hyperparameters and the threshold were picked on validation; the held-out test set was evaluated a single time at the end, so it didn't leak into any choice.
- **Measure cost and latency, not only accuracy.** A slightly more accurate model that is much slower or costs money per request may be the wrong thing to ship.
- **Plan for "I don't know".** Below the 0.69 confidence threshold the API answers `out_of_scope` instead of a confident wrong intent.
- **Cache every LLM answer.** Each answer is stored as one JSON file, so re-running the evaluation makes no API calls. To stay on the free tier, the LLM ran on a fixed 400-query test sample.

Local latency is one request at a time on an Apple M5 CPU; LLM latency is the network round trip. LLM cost uses Gemini's paid-tier token price; the runs themselves used the free tier.

- **Fine-tuned DistilBERT is the one to ship** with about 100 labelled examples per intent: the most accurate, about 130x faster than the LLM, and free per request.
- **The threshold matters as much as the model.** It lifts out-of-scope recall from 0.59 to 0.78 for under 1 point of in-scope accuracy.
- **The LLM is the best out-of-scope detector with zero training** (recall 0.83), but it is slower, costs money per call, and is weaker on near-identical intents.
- **Most errors are out-of-scope queries** that look like a real intent (for example "where can i buy new shingles" predicted as `order`). The most confused pair of real intents is `redeem_rewards` → `rewards_balance`.

## Limits and what I'd do next

- The LLM was measured on 400 test queries, not 5,500, so its numbers have wider error bars. Only one LLM and one prompt family were tried.
- Validation has 3% out-of-scope queries and test has 18%, so the best threshold on real traffic depends on how often users go off-topic.
- Probabilities are over-confident. Next: calibrate them (for example temperature scaling), then re-pick the threshold.
- Use the ONNX export for a smaller, faster CPU image; try retrieval-based few-shot examples for the LLM; check the conclusions on a second dataset such as BANKING77.
